How the concealment works

Cryptography, and what Ferdinand actually does with your password.

This page explains the ideas behind encryption in plain terms, then walks through the exact steps Ferdinand takes when you conceal or reveal something — and how to use the tool itself.

01

The basic idea

Cryptography turns readable content (plaintext) into content that looks like noise (ciphertext), in a way that's only reversible if you hold the right secret. Ferdinand uses symmetric encryption: the same password both conceals and reveals the content. There's no separate "public" and "private" key pair here — just one password, held by whoever should be able to read the message.

Key

The actual secret used to scramble data. It's not your password directly — it's derived from it.

Salt

Random bytes mixed into your password before deriving a key, so the same password never produces the same key twice.

IV / nonce

A random value used once per encryption, so encrypting the same text twice still gives different ciphertext.

Auth tag

A built-in checksum that lets decryption detect tampering or a wrong password, instead of silently returning garbage.

02

What happens when you conceal something

Ferdinand runs entirely in your browser — nothing you type or upload is sent anywhere. When you press conceal, four things happen in order:

  1. Random salt and IV are generated

    The browser's cryptographic random number generator produces a fresh 16-byte salt and 12-byte IV — different every single time, even for the same password and message.

  2. Your password becomes a real key

    The password itself is never used to encrypt anything directly. It's stretched into a 256-bit key using PBKDF2, repeated 150,000 times over, so guessing passwords by brute force is deliberately slow.

  3. The content is encrypted with AES-256-GCM

    Your text, image, audio, or video bytes are encrypted directly — no intermediate re-encoding — producing ciphertext plus an authentication tag.

  4. Everything needed to reverse it (except the password) is packaged together

    The salt, IV, and ciphertext are bundled into one block of text. That block is what you see, copy, download, or share — the password never travels with it.

Reveal runs the same steps backwards. Your password plus the stored salt regenerate the exact same key, and the IV lets Ferdinand decrypt the ciphertext. If the password is wrong, the authentication check fails immediately — Ferdinand tells you it can't be revealed rather than showing corrupted content.

03

Text, images, audio, and video — secured the same way

AES-256-GCM doesn't care what the bytes mean — a paragraph of text and a photograph are both just bytes to it. What changes between media types is how those bytes are prepared beforehand and what gets remembered so Ferdinand can rebuild the file afterward.

Text

Your text is converted to raw UTF-8 bytes, then encrypted directly. A small marker records that the result should come back as text, not a file.

Images

The image file is read as raw bytes and encrypted as-is — no base64 step beforehand, which keeps large photos from ballooning in size before encryption.

Audio

Handled identically to images: raw file bytes in, ciphertext out. The original MIME type (e.g. audio/mpeg) travels alongside, encrypted with everything else.

Video

Same pipeline again. Only the byte size changes — the cipher, key derivation, and password requirement are identical across every media type.

On reveal, Ferdinand checks the stored type marker: txt decodes straight back to text, while bin rebuilds a file from the decrypted bytes and its saved MIME type, then renders it as an image, audio player, or video player inline. Nothing about the security is weaker for media — it's the same key, the same cipher, the same authentication check either way. The only extra ingredient is remembering what kind of bytes they were.

The MIME type is encrypted too. Until someone enters the correct password, Ferdinand can't tell — and won't reveal — whether a concealed block contains a sentence, a photo, or a song.

04

Under the hood

For anyone who wants the exact parameters rather than the plain-English version:

CipherAES-256-GCM — authenticated encryption, so tampering or a wrong password is detected rather than silently decrypted into garbage.
Key derivationPBKDF2, SHA-256, 150,000 iterations — makes brute-forcing the password computationally expensive.
Salt16 random bytes, generated fresh per operation.
IV12 random bytes, generated fresh per operation.
EngineNative browser crypto.subtle (Web Crypto API) — hardware-accelerated, nothing sent over the network.
Payload formatA JSON block carrying version, salt, IV, ciphertext, and a type marker for text vs. image/audio/video.
05

Using Ferdinand, step by step

  1. Add your content

    Type or paste text directly into the document, or use the file picker to load a text, image, audio, or video file (10MB limit per file).

  2. Choose conceal

    Press the conceal action and enter a password when prompted. This password is never stored — remember it, because there's no recovery option.

  3. Save or share the result

    The document now shows a block of ciphertext. Copy it, download it as a file, or use the share action to send it through another app.

  4. Reveal it later

    Paste the concealed block back into Ferdinand, choose reveal, and enter the same password. Text reappears as text; images, audio, and video render inline.

The password is the only key. Ferdinand keeps no copy of it and no way to reset it. If it's lost, the concealed content is unrecoverable by design — that's what makes it secure.
